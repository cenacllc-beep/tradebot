# tradebot: project brief (read completely before doing anything)

(Rebuilt 2026-10-13 after the project folder, paper.db and all backups were deleted by something other than the user or Claude. Rules text recreated from the user's brief and later decisions.)

## 1. Who this is for and what they want
The user wants to make money from trading automation as soon as possible. Small bankroll (about $25), agreed to a short test before any real money. Be straight: at this size even a working edge earns cents to a few dollars, and trading is an unreliable income source. Never hype results, never imply guaranteed profit, gently discourage risking money they need. Not financial advice. Explain results in plain language. The user is on Windows (PowerShell). Project target is Python 3.8 syntax (works on later versions).

## 2. The honest core question
Does a forecast-based estimator beat Kalshi market prices on daily weather markets? Nothing else matters until that is answered. "No edge found" is a valid, useful outcome that costs nothing. Do not try to force a positive result.

## 3. Hard rules (only the user can change these, explicitly)
- Real orders only through live.py (user decision 2026-10-14, replacing "no live order execution"; see section 3a). No other file may place, change or cancel orders. Real money stays locked until the stop date and then needs the user's own typed unlock. Claude never runs `live unlock`, `live resume` or `live use prod`, never pipes input into live.py, never edits live.db or %USERPROFILE%\.kalshi\settings.json by hand, and never loosens a lock or limit in live.py without the user's explicit instruction.
- Never ask for, store, or handle seed phrases or wallet access. The Kalshi private key stays in a file outside this folder (default %USERPROFILE%\.kalshi\) that only live.py reads, to sign requests. Claude never reads, prints, copies, uploads or asks for it; the user never pastes it into chat. Settings (key ID and key file location) live in %USERPROFILE%\.kalshi\settings.json or the KALSHI_ENV / KALSHI_KEY_ID / KALSHI_KEY_FILE environment variables, never in this folder. Kalshi's changelog (June 30, 2026) describes a write::trade key scope (orders without transfers): use it for the real account if offered; otherwise treat a key as full access to the account.
- Never delete or overwrite paper.db. Back it up before bulk file operations, migrations and each scan, and keep a copy OUTSIDE this folder too (the folder was wiped once).
- Limits stay fixed: quarter Kelly, 6% per trade, 10% daily loss limit (net P&L of trades settled in the last 24 hours; when hit, a scan opens no new paper trades but still logs markets), 8-point minimum edge, 50/50 blend, and MAX_OPEN_PCT = 0.15 (total open cost + fees, all versions, may not exceed BANKROLL * 0.15).
- Kill switch: `.\run kill` (or a file named KILL, any case and any ending such as KILL.txt, in the tradebot folder) halts every step that trades: run.bat's scan stops before anything else (backups, the export and the dashboard still run), and main.py, shadow.py and live.py each check it too (live.py again before every order). If the tradebot folder cannot be read, or the check itself fails, the scan does not run (fail closed). Settling still records results; it never trades. `.\run kill status` shows it; check.py reports HALTED so the backup scan does not make up a halted scan. Claude turns it on when the user asks and never turns it off: only the user runs `.\run unkill` (it refuses scripts and asks to confirm) or deletes the file.
- No browser-driven trading, no automated memecoin buying, no leverage.
- Ask before: installing packages or software, downloading anything, touching files outside this folder, changing config.py, or any network call to a new domain. (Approved 2026-10-14: the `cryptography` package and Kalshi's demo exchange external-api.demo.kalshi.co, for live.py. - Never put personal data (email, name) in outbound requests. The only User-Agent allowed is `tradebot-paper-research/1.0`. Do not copy the user's account email from context into any file, log, request or CHANGELOG.
- api.weather.gov is approved only for the NWS rain code (nws.py and the KXRAIN estimator). Keep calls minimal.

## 3a. Kalshi account (live.py; added 2026-10-14 at the user's request)
The user asked for Kalshi "fully integrated by November 11 to fund, open and verify the account" and chose: demo exchange first, real money unlocked by "my call on Nov 11" (the bot shows the gate verdict first), at most $25 at risk.
- live.py copies the paper bot. Right after each scan (`run.bat scan` runs `live.py mirror`) it places the same new paper trades on the connected account: v3 rain markets only, buy only, limit price = the paper price, immediate-or-cancel (nothing rests), count no more than the paper count. It re-reads the market first and skips if the price moved up, the market's day has begun, or the market is missing or closed. Only paper trades opened in the last 12 hours, and after setup, `use` or unlock, are copied. Each paper trade is copied at most once per exchange: live.db's unique index, a client order id fixed per paper trade, and a check on Kalshi itself for an earlier bot order or a position on that market (so a lost or restored live.db cannot cause a second order). A row is written before the order is sent; an order whose outcome is unknown is looked up by its client order id and never re-sent, and while one is unknown no new orders go out. place() re-checks every lock and the match with the paper trade. Each sync compares Kalshi's position in every open market with the ledger (YES positive, NO negative); a difference (a missed fill or a manual trade on that market) stops new orders until a later sync finds them equal or the user types resume. The "already holds this market" check fails closed, because a NO copy is a YES sell.
- Locks: KILL file stops everything. Demo exchange (fake money) works any time. Real exchange only when today >= the stop date (Nov 11, 2026), the exchange is set to prod and the user ran `.\run live unlock` in a terminal (it refuses scripts and piped input, shows the paper gate verdict, says plainly if the gate did not pass, and needs the typed phrase UNLOCK REAL MONEY; the unlock is recorded in live.db and in the settings file, and both must agree). `.\run live lock` relocks at any time, and a restored old live.db cannot undo it.
- Limits: at most $25 at risk across the whole account (MAX_AT_RISK, from Kalshi's own position exposure plus resting buy orders, or the local ledger if higher; orders are cut or skipped to fit, and cash must cover them); daily loss stop (settled losses in the last 24 hours reach DAILY_LOSS_LIMIT x BANKROLL = $2.50); drawdown pause when the bot's value ($25 + settled net) falls 25% below its peak, until the user types `.\run live resume`. Section 11a's doubling rule shows as a reminder in `.\run live status`.
- Ledger: live.db next to paper.db (orders, events), backed up with paper.db by backup.py (exit code 3 = only live.db failed: the paper scan still runs, the Kalshi copy is skipped). `live.py sync` (run by `run.bat settle`) records fills and settlements. live.py never writes paper.db. The dashboard shows a read-only Kalshi account tile.
- Kalshi API: orders go to the V2 endpoint POST /portfolio/events/orders (bid/ask on the YES leg; a NO buy is an ask at 1 - price). The old POST /portfolio/orders answers HTTP 410 (retired 2026). Verified on the demo exchange 2026-10-14 (YES and NO test orders filled; positions +1 and -1). For the real account, use a trading-only key (write::trade scope, no transfers) if Kalshi offers it.
- Commands: `.\run live setup | test | status | demo-order [no] | use demo | use prod | unlock | lock | resume | sync`. Claude may run status, test and sync, and demo-order when the user asks; never unlock, resume or use prod.
- The paper test and the gate are unchanged: live results never count toward the gate, and the rules in sections 5 and 11 still say what a failed gate means. The user decides on Nov 11. Since 2026-10-28 (pre-committed, section 11): after a failed gate look v3 opens no new paper trades, so live.py has nothing new to copy even if unlocked.

## 5. How the test works
- scan logs every evaluated weather market to the shadow log and opens a paper trade only on RAIN markets, only when edge is 8+ points after blending, under the exposure cap. Temperature markets are logged but not traded since 2026-10-14 (user decision after research/PLAN2.md showed Kalshi's temperature prices beat the forecast); the two temperature trades opened before that settle normally.
- A market whose Kalshi day has begun (close_time - 24h) is neither logged nor traded (strategy.started, 2026-10-14).
- Veto since 2026-10-28 (user decision after the audit): no rain trade when the forecast and the market mid are more than 30 points apart (strategy.VETO_MAX_GAP, the selector's frozen ANOMALOUS_MODEL_MARKET_GAP bound). The market is still logged. Trades before and after that date follow different rules; keep them apart when judging the gate.
- settle records outcomes. report compares Brier score of forecast vs market (lower wins).
- Gate before even discussing live money: >=100 resolved v3 RAIN markets, forecast Brier below market Brier by a clear margin, >=50 settled v3 rain trades, net positive after approximate fees. Thresholds do not change.
- "Clear margin" (defined 2026-10-14, before any results existed; the user can change it): take forecast Brier minus market Brier for each resolved v3 rain market, average it within each market day (cities on one day share weather, so each day counts once), and require at least 5 market days with the mean below zero by at least t standard errors of the day means (t = Student-t 97.5% value for days - 1 degrees of freedom, never below 2.0). Judged ONCE, on the stop date (single look, user approved 2026-10-14 after the statistical review showed daily checks raise false passes to about 11%); before that the numbers are interim and the gate cannot pass. strategy.margin/clear/final and dashboard.margin/clear/final implement it. Temperature, v1 and v2 never count. Even then live use starts tiny and needs the user's explicit go-ahead.
- Caveats to mention: cities are correlated; paper results ignore slippage; fees are approximate; early samples are noise.

## 5a. Shadow tests (added 2026-10-14 at the user's request; research only)
(Not the same as the "shadow log" above: that is the obs table of forecast vs market, which feeds the gate's Brier check.) shadow.py runs after main.py in run.bat. It NEVER counts toward the gate, never writes to trades or obs, and never changes v3. Its own tables in paper.db: shadow_orders, shadow_moves (created once, after a backup).
- Price moves: for every v3 obs row, the market's mid when its Kalshi day began (close_time - 24h) vs the mid at our scan, from Kalshi's public minute candlesticks (GET /markets/candlesticks, same API domain). Positive = moved toward the forecast. Computed at settle.
- Limit-order (maker) ledger (rain markets only since 2026-10-14, mirroring the main bot): same v3 forecasts, 50/50 blend, 8-pt edge, quarter Kelly, 6% per trade, own 15% open cap and own 10% daily stop (losses settled in the last 24h), on a separate hypothetical $25. Order = 1c better than the best bid if the spread allows, else join the best bid; cancelled at the day start. Filled only if a minute candle after the order time shows a trade or offer at our price (strictly through it when joined). Maker fee 0 (weather markets are not on Kalshi's maker-fee list). Assumes full size fills and ignores queue size: optimistic on fills, so read fill rate together with win rate.
- Results may justify a future version (for example maker entries as v4). That needs the user's go-ahead and its own fresh test; do not change v3 to match shadow results.

## 6. Change discipline
- Only fix clear bugs; never tune to match the market or past results. Derive fixes from definitions. Log every change in CHANGELOG.md with a timestamp and tell the user before editing; show diffs when asked.
- Estimator changes create a new version tag and old rows keep their tag. v1 = Open-Meteo peak-hourly rain; v2 = NWS 12h periods (6am-6am); v3 = NWS hourly gridpoint slices aligned to Kalshi's day (FROZEN). After implementing a version, do not iterate; report and stop.
- Scans must run BEFORE Kalshi's day window starts (close_time - 24h); the code skips a market otherwise.
- Run `python dashboard.py --no-open` after each scan, settle and report.
- Independent review (added 2026-10-14 at the user's request): before acting on a research result or shipping a change to the bot, a fresh agent that has not seen the work reviews it with agents/statistician.md (results, test designs) or agents/code-reviewer.md (code). Reviewers only read and report. Record the findings and what was fixed or deliberately left in CHANGELOG.md.
